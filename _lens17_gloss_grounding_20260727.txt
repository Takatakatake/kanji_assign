■ なぜこのレンズが新しいか

第1〜16レンズは、突き詰めると全て【内部整合】の測定だった。
  被覆 / 構造 / 裸字率 / 語完読 / 適否 / 実文token / 学習ROI / 識別子勾配 /
  一意性 / 棚卸し / 別AI検証 / 学習順序 / 版間整合 / 配信面 / 多義裁定 / 逆引きround-trip
どれも「割り当て表と注入結果が自分自身と辻褄が合っているか」を見ている。
つまり、割り当てそのものが全部間違っていても全部PASSしうる。

本レンズだけは、プロジェクト外部にある独立した正解データと突き合わせる。

  (Z) CSV2890 の Chinese_Trans 列
      … 簡体字。割り当て字と【全く同じ字種】(通用规范汉字表)なので直接照合できる。
      ★このプロジェクトのスクリプトはこの列を一度も読んでいない。
        パイプラインが CSV から読むのは Esperanto 列と Unified_Level 列だけ
        (Japanese_Trans は _gen_html_view_id.ps1 の表示用のみ)。
        つまり機械的な循環参照はない = 独立した検証たりうる。

  (J) 学術版原本の日本語訳
      … 全44,000語超で使えるが、日本漢字なので簡体字の割り当てとは字体がずれる
        (異/异・顔/颜・築/筑…)。過小評価になる。

同じCSV2890語で(Z)と(J)の両方を測れば、その比が「字体差による目減り係数」になる。
実測 = 2.21倍。(J)しか使えない層の数値はこの係数で読む。

さらに chance level(偶然一致率)を実測した。割り当て表を固定オフセット499で
巡回シフトし、無関係な語根の字を当てて同じ照合をかける。
接地率が chance と変わらなければ「意味が合っている」とは言えないからである。

■ ★短いトークンという希少資源の配分 — 優先順位の直接測定
--------------------------------------------------------------------------------

1字トークンは有限の希少資源である(一级3500字)。優先順位が本当に効いているなら、
上位層ほど1字を占め、下位層ほど長い合成トークンに回っているはずである。

層                       語根数    平均字数     1字率    3字以上率
tier0_CSV2890内容語        2512    1.07字    93.0%     0.4%
tier0b_機能形態素            183    1.18字    82.0%     0.0%
tier1_PEJVO              4384    1.54字    54.5%     7.5%
tier2_PIV                3154    1.57字    54.5%    10.6%

★ 単調。CSV2890層は93.0%が1字を確保し、3字以上はわずか0.4%。
   PEJVO/PIV層に落ちると1字率は54.5%まで下がり、3字以上が7.5%→10.6%と増える。
   希少資源が優先順位どおりに配分されている、という定量的な証拠。

   なお tier1 と tier2 の1字率は同値(54.5%)で、両層の差は3字以上率にしか出ない。
   第2層と第3層の境界は、トークン長では弱くしか効いていない = advisory。

■ ★唯一の実質的発見: limak = 蜗牛 (誤友)
--------------------------------------------------------------------------------

  helik/o = カタツムリ(蜗牛)      → 螺ᴴ
  limak/o = ナメクジ(蛞蝓)        → 蜗牛     ← ★他方の動物の名前そのもの

  CSV2890層(Unified_Level 9.00)の語。中国語訳は「蛞蝓属动物（蛞蝓，也叫蜒蚰，鼻涕虫）」。
  学習者は 蜗牛 を見て heliko と読む。第16レンズの逆引き表でも 蜗牛 → limak と引ける
  ため、round-trip としては壊れていないが、意味としては別の生き物を指している。

  helik=螺 の側は動かすべきでない。helik/a = 螺旋状 という主要語義を 螺 が同時に担って
  おり、これはユーザーの方針(「一つの語根に複数の意味があっても字を増やさない」)の模範例。

  新字ゼロの制約下での選択肢(蛞・蝓・蚰は一级外で使用不可):
    A. 鼻涕虫 … 中国語訳中に実在する語。正確だが3字で俗語的。
    B. 螺ᴸ   … 近縁字(腹足綱)に寄せる。§4.6の科別字と同じ作法。ただし limak は
               band=basic、helik は band=pejvo なので、螺群に入れると limak が
               基本形を奪い helik の識別子が動く(churnリスク)。
    C. 現状維持 … 生物名5基準の「汎用字集中可」の範囲内と見なす。

  → 字選びの裁定事項としてユーザーに提示。単独では変更しない。

■ 測定側で見つけて直したバグ(3件) — 数字を信じる前に必ず潰した
--------------------------------------------------------------------------------

  1. PIV層の接地率が 1.3% と出た。原因は語釈がエスペラント文で漢字を1字も含まないのに
     分母に入れていたこと。「漢字を含む語釈」に限定 → 正しくは【測定不能98.3%】。
  2. それでも tier2 が 1.8% 残った。原因は分野タグ【動】【植】【解】が漢字なので
     aden=腺 が【解】に当たる等の偶然衝突。タグ除去 → 0%。
  3. 語根照合。既存監査(_audit_priority_tiers.py)は語尾を先に剥がすため
     kvin→kvi(=静/kvieta)、tamen→tam(=草) と誤照合していた。
     逆に剥がさない優先にすると ami→伞、fermi→金(fermio元素)、studi→室(studio)、
     taksi→车(taksio)、teni→条虫(tenio) と PIV同綴語に流れる。
     → 「CSV2890行は最上位層の語なので中核band側の解釈を採る」規則に修正。
     ※ 既存の _audit_priority_tiers.py にも同じ癖が残っている(advisory。
        CSV2890語根集合がわずかに膨らむだけで、NEW違反判定には影響しない)。

  誤友検出器も、当初222件のうち大半が arkitekt=建筑 を自分の訳語「建築家」に対し
  筑≠築 の字体差だけで誤検出していた。「1字も接地しない」条件を足して62件に。
